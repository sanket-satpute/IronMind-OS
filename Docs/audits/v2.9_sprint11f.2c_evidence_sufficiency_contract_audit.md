# V2.9 Sprint 11F.2C Evidence Sufficiency Contract Audit
**Status:** EVIDENCE SUFFICIENCY CONTRACT BLOCKED — CONTRACT GAPS REQUIRE REVIEW

## 1. Current Architecture
- **AI Layer:** Generates `PatternCandidate` (hypothesis) and `DiscoveryProposal` (search intent).
- **Domain Layer:** Converts proposal to `DiscoveryCriteria`, orchestrates `EvidenceDiscovery` to fetch bounded `EvidenceReference`s, and (soon) validates them.
- **Data Layer:** Resolves evidence identifiers against durable storage (Events, Observations, Reflections).

## 2. Existing Authoritative Contracts
- "AI proposes. Domain verifies. Evidence proves."
- `PatternCandidate` is merely an AI proposal, lacking authority.
- `EvidenceReference` identifies evidence purely by `sourceId` and `sourceType`.
- AI must NOT dictate confidence, status, or persist `Pattern` entities directly.
- The `PatternEngine` owns the conversion from `PatternCandidate` to `Pattern`.

## 3. What Evidence Sufficiency Means
Evidence Sufficiency answers a specific question: **"Is the valid evidence set quantitatively and structurally sufficient to support this specific `PatternCandidate` under an explicit domain contract?"**
- **Not Discovery:** Discovery only asks "What durable records match the search bounds?"
- **Not Validation:** Validation only asks "Do these records actually exist and belong to the user?"
- **Not Confidence:** Confidence asks "How statistically or empirically strong is this accepted pattern?"
Sufficiency is the absolute boolean gatekeeper prior to Acceptance.

## 4. Authority Boundaries
- **AI Owns:** The hypothesis (`type`, `description`, `conditions`, `predictedBehavior`).
- **Domain Owns:** The discovery bounds, the evidence count, the sufficiency evaluation, the confidence calculation, and the final `Pattern` creation.
- **Boundary Rule:** AI CANNOT claim a pattern is sufficient simply because it generated it. The Domain must independently evaluate the validated evidence against hard thresholds.

## 5. Existing Thresholds
**NO AUTHORITATIVE SUFFICIENCY THRESHOLDS CURRENTLY EXIST.**
A repository-wide search reveals no explicit numeric definitions for pattern creation regarding:
- Minimum evidence count.
- Minimum repetitions.
- Minimum days/temporal spread.
- Source diversity.
**CONTRACT GAP:** We must establish whether 11F.2C should define hard structural thresholds now (e.g., "At least 3 valid evidence items"), or if it should establish the structural interface only and defer the numeric threshold injection to a higher-level policy.

## 6. Temporal Semantics
**CONTRACT GAP:** Currently undefined. 
- Does sufficiency require evidence to span multiple timestamps/days?
- Can a pattern be formed from 3 events that happened in the exact same minute?
- We must explicitly separate "Discovery Bounds" (the time window searched) from "Sufficiency Temporal Rules" (the required spread of evidence).

## 7. Source Diversity Semantics
**CONTRACT GAP:** Currently undefined.
- Is evidence from 1 `OBSERVATION` + 1 `EVENT` inherently more sufficient than 2 `EVENT`s?
- We require an authoritative domain rule determining if source diversity is a factor in sufficiency or only in confidence.

## 8. Contradiction Semantics
`PatternCandidate.contradictionSignal` allows the AI to declare a perceived contradiction.
**CONTRACT GAP:** 
- Can the AI's string signal alone block sufficiency? (Violates domain authority).
- Does the domain need to deterministically resolve the contradiction before declaring sufficiency? If so, we lack the semantic engine to do so purely in the domain layer.

## 9. Evidence Identity
Evidence Sufficiency must evaluate sets of `EvidenceReference` (uniquely identified by `sourceId` + `sourceType`). Deduping must be maintained at the identity level so that 5 references to the exact same Event do not count as 5 distinct pieces of evidence.

## 10. Pipeline Ordering
The required rigid architectural ordering is:
1. `PatternCandidate` & `DiscoveryProposal` (AI)
2. `DiscoveryCriteria` (Domain)
3. `EvidenceDiscovery` (Domain) -> Fetches `[EvidenceReference]`
4. `EvidenceValidation` (Domain) -> Verifies existence, filters invalid.
5. `EvidenceSufficiency` (Domain) -> Evaluates valid count/spread against thresholds.
6. `PatternAcceptance` (Domain) -> Approves candidate.
7. `PatternConfidence` (Domain) -> Computes initial `confidence`.
8. `Pattern` persistence (Domain).

## 11. Proposed Result Contract
`EvidenceSufficiency` must output a structured domain result:
- **Sufficient:** Contains valid evidence count, temporal spread metrics, and authorized source types.
- **Insufficient:** Contains failure reasons (e.g., `InsufficientCount`, `InsufficientTemporalSpread`).
- **Error:** Systemic or malformed criteria errors.

## 12. Error Semantics
Sufficiency must explicitly distinguish between:
- `Result.Success(Insufficient(Reason))` - The evaluation succeeded, but the threshold was missed.
- `Result.Failure(Exception)` - The repository/infrastructure failed during a required lookup.
Repository failures MUST NOT be silently coerced into "Insufficient Evidence".

## 13. Confidence Boundary
Sufficiency is a prerequisite to Confidence. 
- Sufficiency = `Boolean` (Does it pass the minimum bar to exist?)
- Confidence = `Float` (How strong is it?)
Sufficiency MUST NOT return or calculate a float confidence score. AI confidence MUST NOT bypass this layer.

## 14. Persistence Boundary
**Sufficiency MUST NOT persist anything.** It is a pure evaluation function. The resulting boolean gate is passed to `PatternEngine`, which handles the actual `Pattern` creation.

## 15. Determinism/Idempotency
Given the exact same `PatternCandidate` and validated `EvidenceReference` set, the Sufficiency evaluator must return the exact same result. It must not depend on current system time (unless evaluating an explicit recency threshold, which must be passed in as a dependency).

## 16. Privacy Boundary
Sufficiency evaluates metadata (Counts, Timestamps, Source Types). It DOES NOT require raw text payloads, location coordinates, or descriptions. This strict privacy boundary must be maintained.

## 17. Required Tests
Implementation will require testing:
- Zero evidence -> Insufficient.
- Sub-threshold evidence -> Insufficient.
- Met-threshold evidence -> Sufficient.
- Duplicate references -> Counted as 1, Insufficient.
- Malformed candidates -> Error.
- Temporal spread constraints (once defined).

## 18. Architectural Placement
Belongs in the domain layer: `com.sanket_satpute_20.ironmind.domain.engine.EvidenceSufficiencyEvaluator`.

## 19. Contradictions/Gaps
1. We have no defined quantitative thresholds for Evidence Sufficiency.
2. We have no defined temporal spread requirements.
3. We have no defined source diversity requirements.
4. We lack a deterministic mechanism for verifying the AI's `contradictionSignal`.

## 20. Explicit OPEN QUESTIONS
1. **Numeric Thresholds:** Should we hardcode a basic threshold (e.g., `minEvidenceCount = 2`) for 11F.2C, or parameterize it completely?
2. **Temporal Spread:** Is there a minimum time delta required between evidence items to prove a "pattern" rather than a single isolated incident?
3. **Contradictions:** How should the domain treat `contradictionSignal` during sufficiency evaluation?
