# V2.9 Sprint 11F.2B.3.1 Order Direction Contract Repair Audit

## 1. Previous Ambiguity
Previously, the order direction of the secondary (`sourceId`) and tertiary (`sourceType`) tie-breaker keys was undefined when the primary order was `TIMESTAMP_DESC`. It was completely ambiguous whether the tie-breakers mirrored the timestamp direction or remained strictly ascending.

## 2. New Permanent Ordering Contract
The permanent contract explicitly defines that the secondary and tertiary tie-breakers ALWAYS remain strictly ascending, regardless of the primary timestamp direction.

## 3. ASC Semantics
`TIMESTAMP_ASC`: `timestamp` ASC → `sourceId` ASC → `sourceType` canonical ASC

## 4. DESC Semantics
`TIMESTAMP_DESC`: `timestamp` DESC → `sourceId` ASC → `sourceType` canonical ASC

## 5. sourceId Direction
The `sourceId` direction is now permanently defined as **ALWAYS ASC**.

## 6. sourceType Direction
The `sourceType` direction is now permanently defined as **ALWAYS ASC** (canonical).

## 7. Canonical sourceType Ordering
The canonical order is explicitly mapped as: `EVENT` < `OBSERVATION` < `REFLECTION`. This must not rely on enum ordinal or string collation.

## 8. Repository Contradiction Search
**BLOCKED — CONTRADICTION FOUND**

A repository contradiction search was performed against the existing Room DAOs (`IronMindDao.kt` and `ObservationDao.kt`).

The prompt stated: *"Because EvidenceDiscovery has not yet been implemented, there should be no production implementation that contradicts this. If a contradiction exists: STOP and report it. Do not silently reconcile it."*

**Contradiction Identified:**
The existing time-window DAO methods added during Sprint 11F.2B explicitly use `id DESC` for their descending queries, which violates the newly established `sourceId ASC` contract for `TIMESTAMP_DESC`:

- `IronMindDao.kt`: `ORDER BY createdAt DESC, id DESC LIMIT :limit`
- `IronMindDao.kt`: `ORDER BY occurredAt DESC, id DESC LIMIT :limit`
- `ObservationDao.kt`: `ORDER BY occurredAt DESC, id DESC LIMIT :limit`

Because this directly contradicts the new `sourceId ASC` requirement, I am stopping as instructed.
